# Adriana So Portfolio V2

## 1. Overview

A personal portfolio for Adriana So showcasing selected product design, AI interaction, and research work.

The portfolio should feel like **a personal digital environment rather than a traditional UX portfolio template**. Its visual identity draws selectively from Y2K computing, cybercore, early digital interfaces, and experimental editorial design while keeping the actual project work clean and authentic to its original context.

The site should communicate three things quickly:

1. **Adriana is a strong product/UX designer.**
2. **She understands and works with emerging AI technology.**
3. **She has a distinct point of view as a designer.**

The portfolio itself can be expressive. The projects should remain faithful to the users, brands, and contexts they were designed for.

# 5. Hero Experience

## Concept

The centerpiece of the homepage is a **large retro-futuristic computer display / CRT-inspired screen**.

It should occupy approximately **60–80% of the initial viewport** and function as the primary visual object.

The object should reference retro computing without becoming a literal recreation of a specific historical computer.

Potential qualities:

* dimensional monitor frame
* slightly curved display
* subtle screen glow
* restrained scanline/noise treatment
* soft plastic, metallic, translucent, or off-white material
* small hardware details
* contemporary proportions mixed with retro cues

Avoid excessive nostalgia decoration.

The desired feeling is:

> **A computer imagined somewhere between the early internet and the near future.**

# 19. AI Architecture

The conversational portfolio is a **real LLM assistant grounded by retrieval (RAG)** over an approved knowledge base. It must **never hallucinate facts about Adriana**, must prefer short answers that surface navigation, and must degrade gracefully to a scripted mode if the API is unavailable.

## 19.1 Goals & guardrails

* Answers are grounded **exclusively** in the approved knowledge base (§24.3).
* The model may rephrase/summarize retrieved content but must not invent facts (titles, dates, metrics, employers).
* Every substantive answer should, when relevant, return **structured navigation targets** (project/experiment links) alongside prose.
* Short responses by default (target ≤ 3 sentences); link out rather than write essays.
* Out-of-scope / unknown → deterministic fallback copy:
  > I don't have anything about that in this portfolio — but you can explore my work below.

## 19.2 Pipeline

```
User message
  → moderation / length guard
  → embed query (embeddings model)
  → vector retrieval (top-k chunks from approved KB)
  → build grounded prompt (system + retrieved context + few-shot format)
  → LLM (streaming)
  → parse response → { answer, citations[], suggestedDestinations[] }
  → render prose + destination chips in CRT
```

* **Embeddings + index:** knowledge base is chunked, embedded at build time, and stored as a static vector index shipped with the app (small corpus → in-memory cosine similarity is sufficient; no external vector DB required). Rebuilt whenever content changes.
* **Retrieval:** top-k (default k=6) chunks with a similarity floor; if nothing clears the floor → fallback.
* **Grounding:** retrieved chunks are injected into the system prompt with instructions to answer only from provided context and to emit destinations by stable `slug`.

## 19.3 Response contract

The route returns a typed object the UI renders deterministically:

```ts
type PortfolioAnswer = {
  answer: string;                 // concise, grounded prose (streamed)
  suggestedDestinations: {        // rendered as clickable chips / "View project →"
    label: string;                // e.g. "WAKEFERN / SHOPRITE LPGA"
    href: string;                 // internal route, e.g. /work/wakefern-lpga
    kind: "work" | "experiment" | "about" | "resume";
  }[];
  citations: string[];            // KB chunk ids used (for debugging/eval)
  fallback: boolean;              // true when scripted/unknown path taken
};
```

## 19.4 Prompt design (system prompt outline)

* Role: "You are the portfolio guide for Adriana So. Answer only from the CONTEXT."
* Rules: no fabrication; prefer brevity; always surface a relevant destination when one exists; if unsupported, return the fallback line and generic destinations.
* Format: instruct the model to return the fields in §19.3 (structured output / tool-style).
* Few-shot: include the Wakefern example from §6 as the canonical answer shape.

## 19.5 Fallback / degradation (must-have)

If the LLM API errors, is rate-limited, times out, or the key is absent:

1. Match the query against a small **intent table** (shipped work, product design, AI research, technical/build, contact/résumé).
2. Return the intent's canned answer + destinations with `fallback: true`.
3. If no intent matches → the §19.1 unknown line + top navigation chips.

The suggested entry-point buttons from §6 always work via this table even with zero AI availability.

## 19.6 Abuse, cost & privacy controls

* Rate limiting per session/IP on the chat route.
* Max input length; strip/reject prompt-injection attempts targeting the system prompt.
* No storage of conversation content beyond ephemeral request handling (see §29); no PII collection.
* Server-side API key only (never exposed to the client).

## 19.7 Evaluation

* A fixture set of representative questions with expected destinations and "must-not-say" assertions.
* CI check: fallback path renders correctly with the API disabled.
* Manual grounding review: sample answers must cite real KB chunks.

# 26. Design Tokens

Concrete implementation of §11–14. Base palette restrained; one accent system; projects override with their own brand accent.

## 26.1 Color (base)

| Token | Role | Value (starting point) |
| --- | --- | --- |
| `--bg` | off-white base | `#F4F2EC` |
| `--fg` | near-black text | `#111214` |
| `--muted` | gray/silver | `#8A8D93` |
| `--line` | thin technical rules | `#D8D5CC` |
| `--metal` | muted metallic | `#B9BCC2` |
| `--accent` | single distinctive accent (TBD, §13) | placeholder |
| `--screen-glow` | CRT glow (decorative) | low-alpha accent |

Per-project `brand.accent` overrides accent inside case studies only. Enforce WCAG-conscious contrast on all text (§17).

## 26.2 Typography

* **Display/editorial** typeface: titles, statements, headings, case-study storytelling.
* **Monospace/system** typeface: chat, metadata, numbering, labels, system messages.
* Fluid type scale (clamp-based). Monospace dotted-leader labels rendered by `MetaList` (`PROJECT........01`).
* Body typography must remain highly readable (§17).

## 26.3 Spacing, grid, motion

* Shared editorial grid; projects vary composition within it (§8).
* Motion tokens: `--dur-fast`, `--dur-base`, easing curves; all decorative motion disabled under `prefers-reduced-motion` (§15, §17).
* CRT effects (glow, noise, scanline, flicker) are decorative-only, `aria-hidden`, GPU-friendly, and excluded from the accessibility tree (§17, §20).

# 29. Security & Privacy

* LLM/embedding API keys are **server-only** env vars; never shipped to client.
* Chat route: input length cap, per-session/IP rate limiting, prompt-injection resistance (§19.6).
* No persistence of conversation content beyond the request lifecycle; no PII stored.
* Standard security headers (CSP compatible with inline motion needs), HTTPS via Vercel.
* Dependencies kept minimal and current.

# 30. Testing & Quality Assurance

* **Unit:** retrieval (top-k, similarity floor), fallback intent matching, response-contract parsing.
* **Component:** chat renders streamed answer + destination chips; project feature + case study render from schema.
* **Integration:** `/api/chat` grounded happy path and API-disabled fallback path (§19.7).
* **Accessibility:** automated axe checks on every route + manual keyboard-only pass; chat fully operable without mouse (§17).
* **Performance:** Lighthouse budgets (see §31); verify site is complete with chat disabled (§20).
* **AI eval fixtures:** representative questions with expected destinations and must-not-say assertions.
* **Responsive:** desktop CRT vs mobile simplified interface both verified (§16).

# 31. Deployment & Environments

* **Host:** Vercel. `main` → production; PRs → preview deployments.
* **Env vars:** `LLM_API_KEY`, `EMBEDDINGS_API_KEY` (or shared), analytics keys — all server-side.
* **Build step:** `scripts/build-embeddings.ts` regenerates `data/kb-index.json` whenever `content/` changes (run in CI/prebuild).
* **Performance budgets (Lighthouse):** Performance ≥ 90, Accessibility ≥ 95, Best Practices ≥ 95, SEO ≥ 95; LCP < 2.5s on the homepage.
